# Why this case exists

The header cell `t = sum(u where a = 3)` has a bare number on the
right-hand side of a predicate equality. §4.2: `pred-rhs = string /
at-ref`, so `group-call` does not generate the cell, and "A header cell's
right-hand side matches one alternative of `formula` in its entirety or the
cell is refused (§9.20)". §9.20 (`malformed-formula`): "a header cell
containing `=` whose right-hand side is not generated by §4.2's
`formula`."

`t` aggregates `u`, and `u = t + 1` reads `t`, so `t` and `u` are a cycle.
§4.2 rule 9: "A cycle evaluates to `#REF!(cycle)`" and such files "are
**accepted files**, not refusals". A cycle is a value, and a value is what
the cells of an *accepted* file hold. It does not exempt a cell from the
checks that decide whether the file is accepted: §9 is a list of things an
implementation "MUST refuse", and nothing in §4.2 rule 9 or §8 suspends an
entry for a column that turns out to be on a cycle. The precedence §8 gives
`#REF!(cycle)` is over other `#REF!`s ("`#REF!(cycle)` takes precedence over
`#REF!(name)`"), which are values too, not over refusals.

The failure this pins is a reader that finds the cycle first, marks both
columns `#REF!(cycle)`, and never inspects the predicate.

Recognition is a property of the cell's own bytes (§4.2 rule 7 refuses to
let "a formula's *acceptance* depend on the header"), and a cycle is a
property of the header, so it cannot make an ungrammatical cell
grammatical. `a` is stored, so §9.22 does not apply, and nothing else in
§9 does.
