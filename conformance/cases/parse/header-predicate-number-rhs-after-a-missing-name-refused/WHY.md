# Why this case exists

The header cell `t = sum(a where zz = "x" and a = 3)` has a predicate whose
first equality names a missing column, `zz`, and whose second has a bare
number on its right-hand side.

§4.2: `equality = ident *WSP "=" *WSP pred-rhs` and
`pred-rhs = string / at-ref`. `3` is neither, so `group-call` does not
generate the cell, and nor does `expr` (rule 3: a call is the whole formula or
nothing). "**Recognition is whole-cell.** A header cell's right-hand side
matches one alternative of `formula` in its entirety or the cell is refused
(§9.20)". §9.20 (`malformed-formula`): "a header cell containing `=` whose
right-hand side is not generated by §4.2's `formula`."

Recognition is a property of the formula's bytes and never of the header:
§4.2 rule 7 refuses to let "a formula's *acceptance* depend on the header
rather than on its own bytes". So the missing `zz` before the bad equality
changes nothing, whether a reader would have reported `#REF!(zz)` for it or
not. The failure this pins is a reader that checks names before grammar, or
evaluates the predicate left to right and stops at the first unresolved name.

The right-hand side is a stored column, so §9.22 cannot apply, and nothing
else in the file is refused. Column `a` holds `3` in one row, so a reader
that compared numerically would have had a plausible match to report.
