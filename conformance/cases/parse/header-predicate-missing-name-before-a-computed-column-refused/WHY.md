# Why this case exists

The header cell `t = sum(nope where zz = "x" and b = "x")` aggregates a
column that does not exist, `nope`, under a predicate whose first equality
names another missing column, `zz`, and whose second names the computed
column `b`.

§9.22 (`computed-column-compared`): "an equality in a `where` predicate whose
left-hand `ident` ... names a **computed** column (§4.2 rule 5) — in a header
cell and on a declaration line alike". `b = "x"` is that equality. §4.2 rule
5: "The outcome is **refusal** (§9.22), not a value."

The missing names do not rescue the file. §8 makes them values ("A name in
the predicate that does not resolve is `#REF!(name)`, not a refusal", and the
leftmost rule would make `t` `#REF!(nope)`), but a value is what an
*accepted* file's cells hold. §9 is a list of things an implementation "MUST
refuse", and the file meets entry 22; nothing in §8 or §9 lets a broken
reference elsewhere in the formula suspend a refusal. §8 itself separates the
two: "§9.22 is not a counter-example — it refuses a *computed* column in a
predicate because comparison there is on cell text and a computed column has
none, which is a semantic impossibility rather than a broken reference."

The cell is generated by `group-call` (§4.2), so §9.20 does not apply, and
nothing else in the file is refused. The failure this pins is a reader that
evaluates the predicate left to right, meets `nope` or `zz`, settles on
`#REF!`, and never looks at `b`.
`parse/header-predicate-missing-names-before-a-stored-column-accepted` is the
same file with `b` replaced by the stored column `a`.
